# CampusPages security notes

Status key: **T** = covered by automated tests that were run; **B** = checked in a real browser (headless Firefox 158); **D** = design/configuration only; **U** = not verified.

## Controls (specification section 14)

| Control | Status | Where / how |
|---|---|---|
| Private storage, no public URLs | D, U | Cloudinary `authenticated` raw assets; the browser never sees a storage URL. **Not verified against a real Cloudinary account.** |
| Storage credentials server-side only | D | Only in `server/.env`; `.env.example` has placeholders; `.gitignore` excludes env files; logger redacts keys/URLs (T). |
| HTTPS in production | D | Production config requires https origins (T), session cookie is `__Host-`, Secure, HttpOnly, SameSite=Lax (T), HSTS header (T). TLS itself is terminated by the host (Phase 8). |
| Strict CORS + Origin check | T | Allow-list only; unsafe requests from other origins are rejected and audited. |
| CSRF | T | Per-session token in `X-CSRF-Token` on every unsafe method, plus Origin check. |
| Password hashing | T | argon2id (OWASP minimum profile); dummy verification for unknown emails. |
| Session expiry and revocation | T | Idle 60 min / absolute 12 h, TTL index, hashed tokens, logout, **sign out everywhere**, cap of 5 live sessions per user; account status and role are re-read from the database on every request. |
| Login and abuse rate limits | T | Per IP, **per account** (successful logins excluded), global per-IP API limit, per-user content limit, public-endpoint limit. All are per process (see risks). |
| Input validation | T | Strict allow-lists; unknown fields rejected (no mass assignment); operator-injection attempts rejected; ids validated. |
| File validation | T | Extension allow-list, magic bytes, extension/content/MIME agreement, size cap, PDF readable + page cap, image dimension cap; SVG/GIF rejected. |
| Bounded processing | T | PDF parsing runs in a **worker thread** with a time limit and memory ceiling (a runaway parse is killed while the API stays responsive); upload concurrency cap; request timeout (30 s) for ordinary routes; Slowloris-style server timeouts. |
| Safe object keys, no path concatenation | T | Keys are generated by the server; the content route takes only a document id; probing by key/path returns 404. |
| Authorization on every operation, IDOR | T | Per request: session -> active account -> role -> document published and ready *now*. Unknown, draft, unfinished and malformed ids are indistinguishable (404). |
| No open proxy | T | The content route reads storage keys only from the database. |
| No unsafe shared caching | T | Content: `private, no-store`, no ETag. Account/admin JSON: `no-store`. Public metadata only is `public, max-age=30`. |
| Safe publish/unpublish and deletion | T | Only ready documents can be published; deletion removes the stored object first and keeps the record if that fails; sweeper removes abandoned uploads and never overlaps itself. |
| Production-safe errors | T | Generic message for unexpected errors; deliberate errors keep a safe code; request id in `X-Request-Id`; no stack traces. |
| Secret-free logs | T | One line per request; no query strings, headers, cookies or raw ids; redaction of sensitive keys and credential/signature URLs. |
| Security audit trail | T | `login_failed`, `csrf_failed`, `role_denied`, `bad_origin`, `logout_all`, document changes; 90-day TTL; no secrets. |
| Content-Security-Policy | B | `client/public/_headers`: `script-src 'self'`, `style-src 'self'`, no inline script or style allowances, `frame-ancestors 'none'`, etc. The app (theme, PDF.js worker, canvases, image viewer) was run in Firefox with this policy enforced. |
| Dependency review | T | `npm audit` (including dev tools) reports 0 vulnerabilities at the time of writing. See below. |

## Dependency review notes
- **PDF.js:** 5.6.205 has a high-severity advisory (arbitrary JavaScript execution when opening a malicious PDF; affects 5.6.83 up to 6.2.108). The project uses **6.4.299**, which requires Node >= 22.13. The viewer also disables eval and XFA.
- `multer` and `body-parser` had high-severity denial-of-service advisories published during development; fixed by upgrading (`multer` 2.5.0, `body-parser` 1.20.9).
- The dev toolchain (Vite 8, Vitest 5, jsdom 30) was upgraded to clear advisories in esbuild/vitest/tinypool.
- Advisories are published continuously: re-run `npm audit` before every deployment.

## Residual risks and limits (read before deploying)
1. **Delivered content cannot be protected.** Anyone who can view a document can screenshot, photograph or extract it. Watermarks, blocked context menus and no text layer are deterrents, not boundaries. Revocation stops *future* requests only.
2. **Limits and caches are per process.** With several API instances, rate limits, stream caps and the metadata cache are not shared; a shared store (e.g. Redis) is needed before relying on them at scale. Set `TRUST_PROXY=true` behind a proxy or all clients share one IP for rate limiting.
3. **Per-account login limit can be abused** to lock a known email out for one 15-minute window (a deliberate trade-off against credential stuffing).
4. **Cloudinary behaviour is unverified** (signed `authenticated` fetch, `Range` support, PDF delivery enabled, bandwidth/credit cost of streaming through the API host).
5. **No password change/reset, no MFA, no bulk student import**; accounts are created by CLI only.
6. **Accessibility trade-off:** pages are canvas images without a text layer, so screen readers cannot read PDF content.
7. **Browser coverage:** only headless Firefox was used. Chrome, Safari, real devices and screen readers are untested.
8. Frontend and API topology (same origin vs cross-site cookies) is decided in Phase 8; the CSP assumes the API is on the same origin.
